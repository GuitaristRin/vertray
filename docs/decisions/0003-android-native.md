# ADR 0003 · Android 原生版对核心边界的影响

- 状态：已采纳（2026-10-22），补充 [ADR 0001](0001-language.md)
- 背景：作者计划自建 Android Native 版本，地图查询与数据需要复用同一套引擎。

## Ⅰ · 为什么不推翻语言决定

ADR 0001 的判据不是「有几个消费者」，而是**核心到底在算什么**。跨平台能共享的部分是数据与查询（命中、最近入口、连通、路线），不能共享的是渲染：web 用 SVG，安卓用 Compose Canvas，桌面另有实现。

渲染天然分叉，查询天然共享。因此「多一个安卓消费者」影响的是**边界画在哪**，不是**用什么语言写查询**。

## Ⅱ · 两条被收紧的边界

**渲染成为后端，不是产品。**

核心输出平台中立的渲染模型：图层、要素、标注层级、样式 token、缩放分档。SVG 是其中一个写出器（web 后端）；安卓写 Compose/Canvas 后端，读同一个模型。

后果：`data/render/*.svg` 是产物而非契约；核心 API 不得出现 SVG 专有概念（`viewBox`、`<g>`、path 字符串）；样式以 token 表达，不以写死的属性表达。

**查询层可移植，且用夹具验收。**

`src/` 不得依赖 DOM、React、地图库或浏览器 API。任何语言的实现，只要通过 `test/fixtures/` 的同一套输入输出，就视为正确——而不是以「看起来一样」验收。

## Ⅲ · 重复实现的代价

当前查询层约 300 行；加入路线与室内结构后预计 1–2 千行。Kotlin 版只需重写这部分，数据契约（JSON）与夹具不动。

对一个单人项目，维护两份查询实现的税是可承受的，前提是夹具足够严；而引入 wasm + uniffi 的税是一次性的，但会加重**当前唯一在用的宿主**（portal-web 的构建与调试）。

## Ⅳ · 触发重估

出现下列任一情况，改用 Rust 单实现（wasm 供 web，uniffi 供安卓），以现有 TS 为参考实现并用夹具对拍：

- 查询层超过约 2 千行，两份实现的同步成本高过绑定层；
- 安卓原生版要先于 web v1.0 落地；
- 需要在同一进程内与 Sokuou / Zethora 共享空间索引。

## Ⅴ · 明确不做

- **不做 Kotlin Multiplatform。** 它会把数据契约绑进 JVM 生态，web 侧要额外跨编译，换来的只是「一种语言」，而非「一份实现」。
- **不现在重写查询层为 Rust。** 为尚未开始的安卓版付 2–3 倍首期成本，且立刻拖慢唯一在用的宿主。
- **不让数据格式随宿主变化。** JSON 是中立层，任何一端都不应要求它变形。
